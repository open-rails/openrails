# UI library

`@openrails/billing-ui` (`web/billing-ui`) is OpenRails' browser side: a typed
client, React hooks and styled components for a customer's purchase and
self-service, and the staff administration console. Hosts embed it in their own
apps; the standalone server's console (`web/console`) and the hosted payment
page (`web/pay`) are built from it. It ships at OpenRails' version, published to
npm with provenance. Guides: [frontend](../client.md#invoices-and-checkout),
[billing administration](../../web/billing-ui/README.md#staff-administration) and the
[package README](../../web/billing-ui/README.md). Paths starting `src/`,
`tooling/` or `critical/` below are inside `web/billing-ui` unless marked otherwise.

## Concepts

- **Entries**: `/client` (framework-free `createBillingClient`, `BillingError`, `tokenSource`, `redeemAssertion`), `/react` (`BillingProvider`, headless hooks), the root (styled purchase and account components, i18n), `/locales/*`, `/admin` (`AdminConsole`, `BillingAdmin`, `BillingCustomerSummary` and helpers), `styles.css`, `admin.css`.
- **Customer surface**: the `/v1/me` routes, acting on the token's own customer.
- **Staff surface**: the admin, catalog, merchant-config and metrics route groups, as `GET /v1/admin/access` reports them.
- **Wire types**: `src/client/generated/` (`wire.ts`, `routes.ts`, `error-codes.ts`, `currencies.ts`), generated by `internal/contract`.
- **Amount**: an int64 decimal string in the currency's native unit; never a JS number.

## How it works

**Customer client.** `createBillingClient({ baseUrl, fetch | getToken })` gives one method per customer route and public config. Responses are parsed by zod schemas (`src/client/types.ts`) typed against `generated/wire.ts`; an amount must be an int64 string (`isAmount`). Only a GET is retried: once, on a network error, a 502, 503 or 504, or a 429 naming its wait, within `RETRY_BUDGET_MS` (2 s). A write is sent again only after `401 credential_expired`, which the gate answers before the route runs. `tokenSource` keeps the token in memory, fetches the next one `skew` seconds (60) before expiry once for every waiting call, and drives that single resend. Payments and card saves carry the caller's `Idempotency-Key`. Failures become `BillingError` with the server's registry code or a local one (`network_error`, …).

**Customer components.** `BuyButton`, `ProductList`, `InvoicePayment`,
`EmbeddedPayment` and `Cart` buy through invoices (`BuyButton`, `ProductList` and `Cart` pass the host's `attribution` to the invoice, and requests carry the provider's `locale` as `Accept-Language`); `AccountBilling` shows
subscriptions, payment methods and history and runs cancel, resume, plan and card
changes. Card data is tokenized in the PSP's own fields (Collect.js, Stripe
Elements, Basis Theory) and never enters the host page. `InvoicePayment` pays with
`expectedTotal` set to the invoice's total. Amounts are formatted with BigInt
(`amountUnits`, `formatAmount`) at the scale from `OPENRAILS_CURRENCY_SCALES`
merged with `GET /v1/config`'s currencies (`useCurrencyScales`); a Stripe wallet
gets the total in minor units (`amountToMinorUnits`), and none is offered when the
total is not a whole number of them. `BillingNotification` and
`isBillingNotification` word billing notices inside AuthKit UI's inbox;
billing-ui owns no inbox.

**Staff console.** `BillingAdmin` takes `baseUrl`, `auth` (`authFetch`, or
`resourceFetch` with `exchange`), `basePath`, `navigation`, `merchant` or
`merchants`, `appearance` and an optional `queryClient`; each instance owns its
transport and TanStack Query cache. It reads `GET /v1/admin/access`
(`src/admin/lib/capabilities.ts`) and shows only the areas the caller may use:
customer support (customers, subscriptions, payments, invoices), catalog, merchant
configuration (settings, ops: findings, proposals, PSP imports, records, provider
prices, parked) and metrics (dashboard, reports). Hidden areas grant nothing; the
API checks every request. Requests go through `src/admin/lib/api` (`AdminClient`,
`ApiError` with registry codes); most bodies use the generated wire types, while
metrics and dashboard types are hand-written in `src/admin/lib/api/metrics.ts`. The
header bell lists open `requires_review` findings, its count a metrics query
refreshed every 30 seconds. Destructive acts use `TypedConfirmDialog` or a
counted, typed confirmation. `AdminConsole` adds AuthKit's account administration
(optional peer `@openrails/auth-ui`) around `BillingAdmin`.

**Consumers in this repository.** `web/console` composes `BillingAdmin` with AuthKit's members, roles, API keys and account panels into the `/admin` console; `task admin-build` builds it into `web/console/dist`, which the binary embeds. `web/pay` (`@openrails/payment-page`) wraps `InvoicePayment` in the hosted pay page; its build in `web/pay/dist` is embedded by `web/pay/embed.go` (`pay.FS`) and served by `Engine.CheckoutPage` from `Deps.CheckoutAssets`. Its `captchaFetch` resends a pay refused `403 captcha_required` once with the solved token.

**Build checks.** `pnpm build` runs `tooling/check-admin-entry.mjs`, which fails
when the customer entry pulls in admin modules or styles.
`critical/check-package.mjs` exercises the packed artifact's exports.

## Interfaces

- npm: `@openrails/billing-ui@X.Y.Z`, the entries above; peers React 19,
  optional TanStack Query 5 and `@openrails/auth-ui`.
- HTTP used: `/v1/me/*`, `GET /v1/config`, `GET /v1/me/config`, `GET /v1/admin/access`, the staff groups' routes, `POST /v1/metrics/query`, `GET /v1/metrics/dashboard`, `PUT /v1/merchant/dashboard`.
- Go: `Engine.PublicConfig` and `Engine.CustomerConfig` let a server-rendered page
  pass config into `BillingProvider`.

## Guarantees

### 1. Exactly-once provider calls
The client retries only GETs; its one write resend, after `401 credential_expired`,
is safe because the gate refused before the route ran. Pays and card saves carry an
`Idempotency-Key`; `InvoicePayment` mints a new one after a failed pay, and the invoice
refuses a second charge (`invoice_payment_in_progress`, `invoice_not_payable`).
`getInvoicePaymentAttempt` reads a lost pay's outcome; no component calls it.

Checks:
- `send()` in `src/client/client.ts` sets one retry for GET and none for any other method.
- The 401 path resends only on `credential_expired`, only once, only with a `tokenSource`.
- OR-J04-S03 and OR-J04-S04 drive both through a real browser and server.

### 2. Agreement with providers
Does not apply: the UI renders OpenRails' state; `onPaid` is a hint, and hosts confirm access from their own API.

### 3. Exact money
Amounts stay strings until BigInt arithmetic; scales come from the currency
registry; the pay request names the total the customer saw; the one provider
boundary in the browser (a Stripe wallet total) is converted exactly or not
offered.

Checks:
- `formatAmount` and `amountUnits` in `src/lib/money.ts` never convert an amount to `Number`.
- The zod `amount` schema refines `isAmount`.
- `src/invoice-payment.tsx` sends `expectedTotal: invoice.total` and offers no wallet when `amountToMinorUnits` returns null.
- `currencies.ts` is generated from `catalog.Currencies`.

### 4. Access control and tenant isolation
Customer methods call `/v1/me` routes that name no customer; the token decides who.
Staff areas follow `GET /v1/admin/access`, but authority is the API's. The console
exchanges a local session for a token bound to the selected merchant.

Checks:
- No customer client method puts a customer id in a path.
- `capabilities.ts` derives every area from `AdminAccess`.
- OR-J38-S34: a configuration reader sees the ops pages with no actions and writes nothing; Map needs `merchant:catalog:manage`.
- OR-J03-S03: the checkout origin cannot reach the privileged API.

### 5. Contracts match the code
`internal/contract` generates the wire types and route table from the route
catalog, and the error codes and currency scales from their registries; `go run
./scripts/contracts` (and `pnpm contract:check`) fails on a stale file. The package
ships at OpenRails' version.

Checks:
- Each generated file's first line says "Do not edit", and `internal/contract/contract.go` lists it.
- `scripts/check.sh browser` runs `contract:check` and builds the console and `web/pay` against this package.
- OR-J04-S01: the built client and real HTTP return the same outcomes.
- `src/admin/lib/api/metrics.ts` duplicates generated types; compare it to `wire.ts`.

### 6. Data lifecycle
Does not apply: the library owns no tables.

### 7. Work scales with activity
Does not apply: no background jobs. An open console polls a running import's progress and the findings count; `InvoicePayment` polls a processing invoice (GET, 10 s) and confirms a Solana invoice awaiting its wallet (`POST …/confirm`, 3 s).

### 8. Abuse protection
The client retries a 429 only for a GET and only when it names its wait; the only
repeated write is `InvoicePayment`'s Solana confirm poll; `captcha_required` reaches
the caller as a typed error, and the pay page resends once with a solved token.

Checks:
- `retryDelay` returns null for a 429 without `Retry-After`.
- `web/pay/src/captcha.tsx` resends only on `403 captcha_required`, once.

### 9. Destructive-action safeguards
The UI confirms before destructive acts and gives no way around the server's
admission and holds: Apply needs the PSP key typed, approving proposals that end
access, move money or write to a provider needs their count typed, and ending
access says what the customer loses.

Checks:
- `TypedConfirmDialog` guards an import's Apply (`src/admin/pages/imports/detail.tsx`), ending a membership (`src/admin/pages/subscriptions/detail.tsx`) and deleting an alert webhook (`src/admin/pages/settings/notifications.tsx`).
- OR-J38-S32: an access-ending approval is held and dismissing needs notes.
- OR-J38-S41: ending access states its effect; clearing a hold confirms it.

## Tests

- `TestPublicSDK` (OR-J04-S01, OR-J04-S03, OR-J04-S04) runs
  `critical/client.spec.ts` in Chromium against an OpenRails engine over real HTTP
  and PostgreSQL.
- `TestMerchantConsole` (OR-J38-S30 to OR-J38-S34, OR-J38-S41) runs
  `critical/admin/console.spec.ts` against the built admin.
- `TestHostedBrowser` (OR-J03-S04) runs `critical/hosted/checkout.spec.ts`;
  `TestHostedCheckout` (OR-J03-S01, OR-J03-S02, OR-J03-S03, OR-J03-S05) serves the
  built `web/pay/dist`. OR-J01-S09 calls the built client from the
  repository's `critical/customer_binding_sdk.mjs`.
- Static: `pnpm critical:static` (typecheck, lint, `check-package.mjs`), the
  admin-entry check in `pnpm build`, and `pnpm contract:check`.
- Gaps: billing-ui has no unit tests. `web/pay` has no Playwright suite of its own, and nothing in the repository runs `server/ci/paymentpage`. No browser scenario opens the catalog beyond a price's Verify, or the payments, reports or alert settings pages, edits a dashboard, or checks the locale bundles.
