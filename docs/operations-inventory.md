# OpenRails operations inventory

This source inventory covers the provider calls and local state changes OpenRails' source can make. It records what the code can do, with the initiating path and the external effect. Account configuration, credentials, routing, permissions, and worker deployment determine which paths a running installation uses. The evidence is repository source and configuration documentation.

A **read** retrieves facts or simulates a transaction without submitting it. A **write** creates, changes, cancels, deletes, authorizes, or submits something on the provider side, including writes that move no funds. That distinction is independent of HTTP method. A read can still produce local records and findings, or record a settlement already confirmed by the provider. A provider intent is an OpenRails ledger entry in `billing.provider_intents`. Some direct calls have other durable records, such as a checkout attempt or capture session. An externally completed action can settle after the initiating OpenRails request returns. ### What initiates provider traffic

- **Provider refresh and operator imports.** Nothing schedules a provider refresh: an operator requests one per merchant with `openrails provider-refresh --merchant`, and its job reads configured accounts in windows and advances provider watermarks as it records evidence. Operators can independently start a PSP import or reconciliation read. ### Account, credential and write controls

- A PSP account belongs to a merchant and has a rail, its provider account ID and an environment. The selected PSP and any custodian identity are carried into attempts, intents, and provider routing. Rotating credentials within that scope preserves the account. Archived accounts can still service existing obligations. Stripe verifies account and test/live identity, NMI qualifies the specific gateway credentials, CCBill uses the account/subaccount and DataLink access, and Solana checks RPC genesis and resolves merchant-specific treasury/signer configuration. A credential check or receipt read may still run when writes are unavailable. [Account operations](standalone.md#provider-intents) · [Environment checks](client.md#merchant-configuration-and-psps) · [Rail resolution](../internal/railresolve/railresolve.go) · [Solana RPC resolution](../internal/modules/solana/merchant_rpc.go)
- The deployment and merchant write modes are `full`, `limited`, and `readonly`. A copied-book hold can further restrict writes. The intent runner holds system-origin writes in `limited` and holds all origins in `readonly`. Direct paths have their own checks. Provider-side work already handed off and existing provider-owned schedules may still complete. ## Prepare a legacy billing rehearsal

Give the rehearsal an ID and note the observation window. It can cover the
import and several days of workers. Link the import, job, and intent IDs to
that rehearsal in the report.

1. **Choose the source and target.** Record the exact legacy snapshot, merchant,
   PSP account, snapshot horizon, host version and OpenRails commit. Prepare an
   isolated database, a dedicated River schema and a separate configuration.
   Use a database backup for the source. `openrails billing export` sets a hold
   on the source merchant. [Archive and restore](standalone.md#backup-and-restore)
2. **Check the fences.** Configure `provider_write_mode: readonly`. Exclude live
   provider credentials from the first phase. Block provider, email and host
   callback egress. Confirm the target database and `openrails book status`
   before importing. [Safety levers](standalone.md#write-safety-and-the-kill-switch)
3. **Prepare the evidence.** Take an access and billing baseline and install a
   committed-row capture on the rehearsal copy before any import. Preserve
   customer and provider references inside restricted evidence storage. Share
   redacted summaries. Checkpoint after import, after a chosen billing pass and
   at the end of the observation window. Capture actual database changes and
   effective access at the same clock instant in before-and-after comparisons.
4. **Collect provider observations.** Save `openrails intents --merchant …
   --status all --format json` and `openrails intents-log --rail nmi`. The
   intent records cover accepted operations. To capture direct writes that
   would have been sent, the rehearsal also needs decision logging before
   write holds. Record a blocked required read with the missing evidence and
   reason. Keep the redacted egress record as the independent send check.
   [Provider intents](standalone.md#provider-intents)
5. **Review a later NMI pull.** With separate approval, attach scoped live NMI
   reading credentials to the isolated environment and allow only the required
   reporting and read requests. Keep provider writes held. Stage a PSP import
   and review the identity matches, proposed access effects and receipt
   differences before applying anything. [Staged import](../internal/pspimport)

The target, source snapshot, and observation cutoff belong in the same report
as the access diff, queued intent export, would-send decisions, blocked reads,
and egress receipt. A separate rehearsal from a fresh snapshot gets its own ID.
